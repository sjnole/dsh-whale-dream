# 鲸梦 0.8.3 · 性能与稳定性报告

本轮以已交付的 0.8.2 为基线，检查全部 38 种外观的绘制开销，并修复隐藏重绘、重复尺寸通知、缓存释放和静态画面跳变问题。优化保留现有外观、完整窗口尺寸、主体数量、点击动作和游戏进度；没有增加新的性能设置页面。

**当前已测的是同一执行环境中的真实渲染器、不同视口与缩放负载，以及生命周期压力场景。没有把这些结果当作多台低配、中配、高配电脑或 Windows DSH 的实机测试。** 随包提供独立离线自检 HTML，方便在目标电脑上取得可比较的数据。

## 一、已完成的验证

**整包检查 419 / 419 通过，0 失败、0 跳过。** `npm run check` 同时完成 TypeScript 检查、生产构建、预览与自检页导出。完整测试阶段耗时约 115.51 秒。

- 全部 38 种外观采用真实生产绘制路径，分别记录 0.8.2 与 0.8.3 的固定负载耗时。
- 重点外观采用旧 → 新 → 新 → 旧的顺序重复测量，降低执行先后、缓存和环境波动造成的偏差。
- 分辨率矩阵使用同一逻辑场景，记录请求 DPR、实际 DPR、真实创建的画布尺寸及已知数组容量。
- 资源与稳定性检查覆盖 152 次外观更换、30 次热重载、500 次点击尝试、重复尺寸通知、输入暂停、隐藏恢复和大时钟跳跃。
- 深浅色与高 DPI 对照使用原生 Canvas 输出；最终植物对照图已经人工查看。

模拟时钟跨过八小时用来验证恢复时不会重演后台时间，不等于真实连续运行八小时。测试中主动保留已销毁 Canvas 的引用，用来检查其像素尺寸是否归零；这能验证相应缓冲的主动释放，不能证明整个 DSH 进程不存在任何内存问题。

### 计时如何解读

测量环境为 Linux x64、Node 24.22.1、`@napi-rs/canvas` 0.1.100。全部性能任务顺序运行，计时期间不同时执行整包测试、构建或打包；云端系统调度仍可能波动，因此保留原始样本和重复运行范围。

默认测量条件为 1920×1080 CSS 像素、DPR 1、固定 30 FPS 时间序列、场景密度 2；海洋为 2 只主体、80 条鱼、大小 1.2。每项先预热 30 帧，再采集 120 帧。分辨率矩阵每次预热 12 帧、采集 48 帧，采样范围比完整筛查短。

每帧耗时包括实际状态推进、清屏和绘制，并读取 1×1 像素等待原生光栅工作完成。p50 是中位数；p95 表示该次样本中约 95% 的帧不超过这一耗时。少量帧的 p95、最大值会受系统调度影响，应该与重复运行范围一起看。全 38 项前后筛查用于寻找热点；较严格的优化对比采用交错重复测量，不把两个不同时段的单次结果全部解释为代码收益。

这些毫秒数是 Node Native Canvas 的工作耗时，**不能取倒数当作浏览器或 DSH 的实际 FPS**。浏览器的 GPU、异步绘制提交、宿主消息排版、毛玻璃和窗口合成均不在该计时中。它也不能表示整机 CPU 百分比。

### 高 DPI 缓冲预算

新版把动态背景的内部像素数量控制在约 829 万，逻辑场景仍使用整个会话窗口。该限制只改变超过预算时的内部光栅精度，不改变主体大小、点击坐标、游戏棋盘、数量和位置规则。

| CSS 视口与请求 DPR | 旧版内部尺寸 | 新版内部尺寸 | 单张 RGBA 理论容量，旧 → 新 | 变化 |
| --- | --- | --- | ---: | ---: |
| 1366×768，DPR 1 | 1366×768 | 1366×768 | 4.00 → 4.00 MiB | 不变 |
| 1920×1080，DPR 2 | 3840×2160 | 3840×2160 | 31.64 → 31.64 MiB | 不变 |
| 2560×1440，DPR 2 | 5120×2880 | 3840×2160 | 56.25 → 31.64 MiB | 减少 43.75% |
| 3840×2160，DPR 2，极端负载 | 7680×4320 | 3840×2160 | 126.56 → 31.64 MiB | 减少 75% |

RGBA 理论容量按宽 × 高 × 4 字节计算，不含浏览器副本、图形驱动、合成器和其他对象。海洋还有同尺寸离屏底图，两张全幅画布在最后一项中的理论合计为 253.13 → 63.28 MiB；字形图块和网格数组另计。内部精度降低可能让高缩放背景细节略柔，但没有把新会话场景缩成小舞台。

显示器的物理分辨率和浏览器 CSS 视口不是同一概念。比如“3840×2160 CSS、DPR 2”实际请求的是 7680×4320 缓冲，不能直接写成普通 4K 显示器负载。

## 三、实际修复的 bug 与资源问题

| 问题 | 原因或复现 | 本版处理与验证 |
| --- | --- | --- |
| 相同尺寸反复触发昂贵工作 | 海洋收到相同 ResizeObserver 通知，仍重设画布并重建网格 | 相同宽高与 DPR 直接返回；真实尺寸变化仍会重绘，输入暂停和场景时间保留。 |
| 隐藏外观仍消耗绘制资源 | 非海洋隐藏后，设置更新仍触发绘制；海洋颜色更新会重画离屏底图 | 合并改动到下一次可见绘制；隐藏和离屏时不执行相应绘图。 |
| 暂停后恢复可见可能缺少当前画面 | 减少动态、输入暂停不会启动持续动画，更新需要独立补画 | 使用待重绘标记；恢复时只补当前帧，不重启暂停动画。 |
| 减少动态时海洋额外跳过约四秒 | 240 步后时间为 3.9999999999999907，旧版小于 4 的判断再次进入稳定化 | 用明确的一次性完成状态，反复改主题或恢复可见保持同一世界时间。 |
| 卸载后的画布资源释放滞后 | 移除 DOM 后仍可能保有主画布、离屏底图与字形缓存 | 主动清零自有画布并释放网格和字形；静态卡片只释放临时资源，保留卡片成品。 |
| 大字号字形缓存占用过大 | 只限制 6000 项，未考虑单张图块大小；达到上限整体清空又造成突发重建 | 同时限制约 16 MiB RGBA 和 6000 项，逐项淘汰。通常 20px 字形仍可保留 6000 项，192px 约 113 项；异常单图块超过预算时最多保留一项。 |
| 相近主题色切换沿用旧花瓣高光 | 植物缓存键遗漏参与绘制的高光色和阴影色 | 补全配色键；相近颜色热切换与冷启动结果一致，新增回归用例。 |

本轮还调整了一个旧测试：其“调整尺寸”操作实际上重复设置同一尺寸。新版去重后，本就不应再次绘制。测试现在分别验证重复通知不重画、真实窗口变化在暂停状态下补画，保留了两个行为的检查。

### 绘制热点优化

颜色解析、确定性的随机种子、主题色板和星云局部几何采用有上限的缓存。极光中不随帧内循环变化的混色计算移到循环外。星空五项在四组深浅色、DPR、互动样例中与旧版逐字节一致。

蒲公英绒球采用有界 Path2D 批量，将代表帧的填充 API 调用从 14,893 次减到 8,028 次，减少约 46.1%；保留底层矩形及透明叠色关系。这是调用数减少，不能直接等同于耗时减少 46.1%。樱花、花野、竹林和荷塘保留逐矩形绘制，避免保留没有收益的批量方案。

四种其他植物在深色 DPR 1、浅色 DPR 1、深色 DPR 2 共 12 个样例中逐字节相同。蒲公英样例约 1.19–1.75% 的画布像素存在微小抗锯齿差异，最大 alpha 差 10/255，平均预乘 RGBA 差低于 0.018/255；对照图中的轮廓、数量和构图保持。缺少 Path2D 时回退原绘法。植物坐标缓存最多 256 个印章、总计最多 65,536 个矩形，坐标缓冲最多约 2 MiB，原生路径内存另计。

## 四、自动性能保护如何工作

当前场景会测量同步绘制成本，持续负载较高时临时降低绘制频率；负载持续降低后再逐级恢复。用户设置的帧率是上限，临时调整不写回配置，不替换外观，不重置场景、点击动作或正在进行的游戏。

控制器使用平滑后的耗时，至少约 1.2 秒、8 次采样才评估一轮；恢复需要连续多个低负载窗口，减少在两个档位之间来回跳动。单次冷启动尖峰、隐藏期间的长间隔和恢复后的空闲时间不会直接被当作稳定性能。

该保护依据的是同步 JavaScript/绘制调用成本，不是 GPU 计时。产品没有为了测性能逐帧读取像素，也不进行硬件型号识别。若卡顿来自 GPU 合成、驱动或宿主的其他任务，仅靠这一控制器不能解决全部问题；像素预算则直接限制背景缓冲的规模。

## 五、不同电脑怎样开始设置

以下是依据负载差异给出的起始建议，不是已测试的 CPU/GPU 机型认证。

| 使用环境 | 建议起点 | 观察与调整 |
| --- | --- | --- |
| 较旧笔记本、集成显卡、同时运行较多任务 | 先设 20 FPS；开启输入时暂停 | 比较静止基线和当前外观的结果；需要时使用现有的数量/丰富程度调节。 |
| 常规 1080p 日常办公 | 从 30 FPS 开始 | 保留喜欢的尺寸和外观，让自动保护处理持续压力。 |
| 2K/4K、高显示缩放、多屏 | 先用 30 FPS，保持自动像素预算 | 同时记录 CSS 视口和 DPR；移动到另一块屏幕后重新测量。 |
| 性能余量较大的电脑 | 先确认 30 FPS 稳定，再试 40 FPS | 观察浏览器回调、长任务和输入感受；不要只看某一次平均值。 |

大型植物、透明光带和字符海洋的负载与小型机器人、部分游戏不同。同类别内部也有差异，因此不能简单认为“游戏一定最耗性能”或“所有植物都一样”。自动降帧优先保留用户选定的美术尺寸与数量，代价是负载高时动画更新次数减少。

## 六、在自己的电脑上运行约 40 秒自检

1. 下载 `whale-dream-performance-0.8.3.html`，在目标电脑用浏览器直接打开。
2. 固定窗口大小和缩放；对比两台电脑时尽量使用相同浏览器版本、电源模式及后台工作负载。
3. 点击“开始测试”。流程依次运行静止基线、座头鲸、樱花树、极光帷幕、星尘怀表城、矿车运星。字体准备时间不计入约 40 秒的阶段时间。
4. 保持当前页面可见。切后台、改变窗口或显示缩放时，页面会中止并注明原因，避免把不同条件混在一份结果中。
5. 点击“导出结果 JSON”。可重复两到三次，看结果是否稳定；不同设置各保存一份。

页面不上传数据，不读用户会话，不调用模型。它加载真实背景挂载层和两种生产引擎，字体嵌入文件；初始状态不会自动运行测试。

结果分别记录浏览器 requestAnimationFrame 回调节奏、实际背景绘制次数、同步绘制耗时的平滑值、临时有效帧率、视口与 DPR。浏览器回调约 60 次/秒而背景绘制约 30 次/秒通常符合 30 FPS 上限，不能把前者当作背景实测 FPS。支持 Long Tasks API 时另记长任务；不支持时明确标记不支持，不把缺失值写成零。

静止基线也出现明显回调停顿时，应先检查当前浏览器和后台负载。某个外观的背景帧率下降、有效上限也同步下降，说明自动保护正在生效。导出文件保留原始环境字段，便于区分窗口、缩放和配置变化。

**自检页不是完整 DSH 压力测试。** 它没有真实长会话的消息 DOM、流式 Markdown 和模型输出，也没有完整主题毛玻璃合成。控制流程、资源清理和生产引擎接入已通过自动检查；当前没有在真实浏览器中执行这份自检页，也没有在用户 Windows EXE 上验收。最终安装后的输入、滚动和整体流畅度仍应在目标客户端确认。
